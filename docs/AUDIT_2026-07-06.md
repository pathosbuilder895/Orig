## 1. Architecture ✅

**Overall assessment.** The live stack has genuinely clean *conceptual* layering — no FastAPI imports in domain code, no raw SQL in the API layer, and a documented (accurate) architecture map — but it is physically concentrated into two god modules (`api.py` 2,714 lines / 60 routes; `store.py` 2,442 lines) held together by module-level global state that assumes a single process forever. About 26% of the Python package (~7,700 LOC) is a dormant parallel backend with its own auth, LTI, schemas, and config, which has already caused one documented incident and still consumes test maintenance. The most acute risks are silent exception-swallowing in the persistence layer (data loss), the process-local cache architecture (blocks multi-worker scaling), and CPU-bound work inside `async` handlers (event-loop stalls).

### A1 — Persistence layer silently swallows all write and load failures — **High**
`store.py:485-495` (`_persist`) wraps the SQLite upsert in `except Exception: pass` with the comment "Non-fatal — data is still live in memory," and `_load_all` (`store.py:470-483`) does the same on load. A full disk, locked DB, or corrupted file means baseline samples and scores appear saved but evaporate on restart — and a corrupt DB silently presents as an *empty institution*. For a FERPA-positioned academic-integrity product, unlogged data loss is the worst failure mode available. **Fix:** log at ERROR minimum, propagate write failures to the caller (API can return 503), and make `_load_all` distinguish "no DB" from "unreadable DB" (fail startup on the latter).

### A2 — `api.py` is a 2,714-line god module: 60 endpoints across ~12 product areas — **High**
One flat file contains staff auth + login throttling (`api.py:428-525`), LTI (`:533-601`), Bluebook exams (`:604-744`), student CRUD/roster, FERPA deletion + data inventory (`:923`, `:1269`), tenants (`:963-1078`), student read-model (`:1145-1265`), baseline ingestion, the 198-line `score_submission` handler (`:1643-1840`), blend detection, Turnitin/Canvas imports, admin manifests/corrections, and the calibration lab (`:2485+`) — plus two middleware, the lifespan/backup scheduler, and 79 `HTTPException` sites. Zero `APIRouter`s; Pydantic models are defined mid-file (`:1447-1462`). **Fix:** split into routers by product area (`auth`, `lti`, `bluebook`, `students`, `tenants`, `scoring`, `admin`, `lab`) mounted on the same app — mechanical, behavior-preserving — and extract `score_submission`'s orchestration into a service function.

### A3 — ~7,700 LOC (26% of the package) is a dormant parallel backend — **High**
Dormant v1 totals 7,689 LOC: `original/api/` 2,843, `original/canvas/` 2,091 (incl. the *other* LTI at `canvas/lti.py`, 724 lines), `original/db/` 904, `original/core/` 627, `original/auth/`+`original/middleware/` 623, `original/schemas_v1/` 368, `original/main.py` 233 — plus 20,914 tracked lines of unserved `frontend/`. Two LTI implementations (`/lti/*` vs `/canvas/lti/*`), two auth systems, two schema sets, two config approaches; `docs/ARCHITECTURE.md:34-36` records a real incident from this. The dormant code is not free: 5 live test files import it, and `cli/security_audit.py:243` audits the *dormant* RBAC middleware as if it protected the pilot. The convergence seam (`repository.py`, ADR-002) covers only 9 methods and its `PostgresRepository` is a `NotImplementedError` skeleton (`repository.py:98-131`) — `api.py:97` still imports `store` directly for everything else. **Fix:** make the decision explicit: quarantine v1 in `legacy_v1/` (or a branch) and drop its tests, or commit to the repository-seam migration with a deadline. At minimum rename to kill the `canvas` name collision.

### A4 — Process-local mutable singletons: correctness assumes exactly one process — **High**
The store loads the *entire database* into a module-level dict on first read (`store.py:48` `_STORE`, `:470` `_load_all`) with no locks; tenant isolation is a string-prefix convention over that flat dict (`store.py:1962-1979`). Also per-process: `_GENRE_STATS_CACHE` (`store.py:57`), login-throttle dict (`api.py:440`), `_REPO` (`repository.py:136`), `_JWKS_CACHE` (`lti.py:173`), `_ENV_CACHE` (`principal.py:133`), feature caches (`features/tier2.py:304`, `tier7.py:24`) — 18 `global` statements. `uvicorn --workers 2` or Render autoscaling would give each worker a divergent `_STORE`: writes in one worker invisible to the other until restart; the brute-force throttle halves. Memory is unbounded — every tenant's every baseline text lives in RAM. **Fix:** document the single-worker invariant in `render.yaml`/`run.py` as a hard constraint now; medium-term, serve reads through SQLite (already WAL) and demote `_STORE` to a bounded cache — this also unblocks the Postgres path.

### A5 — Circular dependency between persistence and scoring domain — **Medium**
`store.py:24` imports `quantum.state`, while `quantum/scoring.py:310,478` import store back (function-local imports hide the cycle). The domain scoring function silently performs SQLite queries mid-computation, so "pure" scoring can't be tested without a database, and the Bayesian prior/fidelity features bypass the repository seam. **Fix:** have the caller fetch genre stats/fidelities and pass them into `score()` as parameters; delete the scoring→store edge.

### A6 — CPU-bound and blocking work inside `async` handlers stalls the event loop — **Medium**
`upload_baseline_batch` (`api.py:2011`) is `async def` but runs pypdf/docx parsing, SHA-256, 103-feature extraction, and sync `store.put()` per uploaded file — all on the event loop, freezing every request (including `/health`) during a multi-PDF batch. Same pattern: `upload_file` (`api.py:1605`), `import_turnitin_csv` (`:2133`), Canvas stubs (`:2204`, `:2221`); the backup scheduler (`api.py:157`) shares the loop. The 53 *sync* handlers are fine (threadpool). **Fix:** drop `async` from these handlers or wrap the heavy loop in `run_in_threadpool` — one line per endpoint.

### A7 — Config is 49 scattered `os.environ` reads with two competing config systems — **Medium**
Env access spans 13 files (49 sites): 22 in `api.py`, and **6 inside the scoring hot path** (`quantum/scoring.py:475-564` reads `BAYESIAN_PRIOR_ENABLED`, `PRIOR_WEIGHT`, `LENGTH_ADAPTIVE_WEIGHTS`, `NULL_MODEL`, `AMPLITUDE_SCORING_ENABLED`, `SECRET_KEY` per call). Two identical `score()` calls can differ because an env var changed between them; there's no single place to see effective config. The dormant stack has exactly the right tool — a validating pydantic `Settings` (`core/config.py:47-65`) — that the live app never uses; `_env.py` is a hand-rolled dotenv. **Fix:** one frozen settings object read at startup; pass flags into `score()` explicitly; per-request env reads only where runtime toggling is deliberate (then document it).

### A8 — Every store operation opens a fresh SQLite connection and replays ~13 DDL statements — **Medium**
`_get_conn()` (`store.py:62-185`) runs `sqlite3.connect` + 3 PRAGMAs + ~13 `CREATE TABLE/INDEX IF NOT EXISTS`, invoked at 30+ call sites — schema migration executes on *every* query, and `with` on a sqlite3 connection commits but never closes. Works at pilot scale; measurable overhead on hot endpoints; makes real migrations impossible to sequence. **Fix:** split schema creation into `init_db()` at startup; use a thread-local connection or `contextlib.closing`.

### A9 — `original/api.py` vs `original/api/` module shadowing requires an importlib hack — **Medium**
The live module's name is shadowed by the dormant package, so `run.py:30-45` loads it via `spec_from_file_location` as `original._legacy_demo_api`. `import original.api` in any script/test/REPL silently imports the *dormant* package; IDE navigation and coverage tools resolve to the wrong code. This is the structural root of the two-backends confusion. **Fix:** rename the live module (e.g. `original/pilot_api.py`) or the dormant package (`original/v1/`); delete the hack.

### A10 — API-contract inconsistency: raw `dict` bodies and partial response models — **Low**
Eight endpoints take `body: dict` with hand-rolled validation — including security-relevant ones: `auth_login` (`api.py:460`), `auth_register` (`:500`), `student_login` (`:1088`), `create_tenant` (`:969`), Bluebook creates (`:624`, `:674`, `:715`) — despite a 650-line `schemas.py`. Error shape is otherwise consistent; roughly half the routes declare `response_model`. **Fix:** define request models for the 8 dict-body endpoints (free 422 validation + accurate OpenAPI); add `response_model` to the rest.

### A11 — `docs/ARCHITECTURE.md` is accurate, with two drift points — **Low**
Claims verify (live app, auth, LTI routes, abandoned `web/`). Omissions: (1) `original/repository.py` is live (`api.py:104`) but undocumented as the convergence seam; (2) the live `/canvas/baseline/*` demo stubs (`api.py:2204-2229`) share a URL prefix with the dormant `original/canvas/` package — exactly the trap the doc exists to prevent. **Fix:** one paragraph covering both.

### A12 — Positive findings (calibration)
Zero `fastapi` imports in `features/`, `quantum/`, `context/`, `store.py`; zero raw SQL in `api.py`; the feature pipeline and quantum modules are cleanly importable domain code. Tenant-isolation and security-header middleware centralized (`api.py:205-283`); lifespan fails closed on missing `SECRET_KEY` in real deploys (`api.py:117-133`); Stage-5 context work parallelized with a bounded `ThreadPoolExecutor` (`context/pipeline.py:213`). The problems are concentration and duplication, not spaghetti — the A2/A3/A9 refactors are mostly mechanical.

### F1 — A third of the repo is dead/dormant, and it still costs CI time and cognitive load — **High**
Dormant v1 Python ≈ 7,900 LOC; dead frontends ≈ 22,800 LOC. No live module imports the v1 stack (verified by grep) — the only bridges are `run.py:174` (non-demo path, unused in prod) and the `PostgresRepository` skeleton. **But** `tests/conftest.py`, `test_api.py` (26), `test_auth.py` (17), `test_canvas.py` (19) import v1 — 62 tests keep SQLAlchemy/pydantic_settings as hard CI dependencies for code no user can reach. **Fix:** delete `frontend/`, `web/`, `legacy_mvp/` (git history preserves them); either commit to the ADR-002 Postgres convergence or excise the v1 package and its 62 tests.

### F2 — Production runs the "demo" app with demo-mode flag forcing; three documented flags are always-on — **High**
`render.yaml:62` (pilot): `startCommand: python run.py --demo --port $PORT --skip-seed`. `run.py:149-155` setdefaults `CONTEXT_MANIFEST_ENABLED=1`, `ADAPTIVE_WEIGHTS_ENABLED=1`, `NULL_MODEL=impostor`. The "opt-in, default OFF preserves Phase 1 byte-identical behaviour" story is fiction in practice — the flag-off path exists only for tests, and the dual-path branching in `/students/{id}/score` (`api.py:1669-1746`) is permanent complexity. **Fix:** declare these three GA, collapse the off-branches, reserve flags for genuinely unproven features (AMPLITUDE_SCORING, BAYESIAN_PRIOR, AI_LIKELIHOOD).

### F3 — Undocumented flags that change scoring math — **High**
Not in the CLAUDE.md flag table: `LENGTH_ADAPTIVE_WEIGHTS` (`scoring.py:515` — rescales the deviation weight vector) and `RANK_REMEDIATION=shrinkage` (`state.py:190` — alters the density-matrix estimator ρ). Both silently change scores if set. Also undocumented: `AI_LIKELIHOOD_ENABLED/SHADOW/MODEL_PATH`, `GUARD_DESTRUCTIVE` + `MAINTENANCE_TOKEN` (`api.py:2642` — a role-granting backdoor password), `ENABLE_HSTS`, `ALLOWED_ORIGINS`, `BACKUP_*`, `BBOOK_*`, 4× `LTI_*`, and the confusing dual `ORIGINAL_ENV` (deploy gate) vs `ENVIRONMENT` (repository seam). ~30 env vars read in the live package vs 7 documented. **Fix:** document all behavior-affecting flags; consider failing startup on real deploys if scoring-affecting flags are set unexpectedly; merge ORIGINAL_ENV/ENVIRONMENT.

### F4 — `original/tasks/` is fully dead and misleads — **Medium**
`tasks/scoring.py` (203 LOC) has zero importers; it imports the dormant v1 `original.db` stack and is keyed to `ENABLE_BACKGROUND_SCORING`, which exists only in v1's config (default True — a flag controlling nothing). **Fix:** delete via `git rm`.

### F5 — Demo/experimental surface in the production app is mostly, but not fully, gated — **Medium**

Gaps: **`operator.html`, `admin-context.html`, `student-coach.html`, `onboard.html`, `landing.html` are served on real deploys** (whole `demo/` static-mounted, `run.py:107`); `landing.html` has zero inbound links (orphaned); two Canvas baseline endpoints are permanent stubs (`api.py:2224`); `run.py:164-165` banner advertises pages that exist only in dead `frontend/`. **Fix:** add operator/admin-context to `_DEMO_ONLY_STATICS` (or staff-gate); delete `landing.html`; remove or 501 the Canvas stubs; fix the banner.

### F6 — Four deploy targets, two aimed at the dormant backend — **Medium**
(Cross-ref B15.) `Dockerfile`+`docker-compose.yml` run `uvicorn original.main:app` — the dormant v1 stack with alembic + Postgres + Redis. `fly.toml` duplicates Render with no pilot flags/hardening. **Fix:** keep render.yaml + Dockerfile.demo; quarantine the rest with the F1 decision.

### F7 — "Experimental" live modules are actually well-wired; only the flag story is messy — **Low**
`tension_arc.py` and `explainer.py` are core scoring dependencies, not experiments. `voice.py` backs the live `/me/*` surface with dedicated leak tests. `lab/` powers staff-gated calibration (5 endpoints, 22 tests) — acceptable at pilot stage. `ai_likelihood.py` is properly shadow-gated with persistence-only shadow mode and 19 tests. `bbook_client.py` no-ops without config. **Fix:** keep all; document the AI-likelihood flags (F3); revisit extracting `lab/` post-pilot.

### F8 — Scoring pipeline: 17 tiers nominally, ~97 of 103 features actually active — **Low**
All tiers extract unconditionally except: **Tier 17 behavioral biometrics (6 features) is in `DISABLED_FEATURE_GROUPS` by default** (`constants.py:364` — "requires live keystroke data from Bbook") → pinned at neutral 0.5 and masked from the density matrix; **Tier 10 semantic (2 features)** degrades to neutral without sentence-transformers. `FEATURE_GROUPS` toggling is a mutable module-global set, not env-controlled. **Fix:** document "97 active / 103 dimensional" in MODEL_CARD-facing docs; consider promoting the group toggle to an env flag if tier 17 comes online mid-pilot.

### T1 — Live pilot backend `api.py` at 61%; whole endpoint groups have zero test execution — **High**
Uncovered blocks map to entire endpoint bodies: Bluebook CRUD (`api.py:625-742`), magic-link baseline request (`:1476-1535`), formation open/advance (`:1573-1599`), single file upload (`:1607-1637`), baseline upload-batch (`:2022-2122`), Turnitin CSV import (`:2141-2192`), and the fail-closed `lifespan` startup checks incl. the "real deploy requires stable SECRET_KEY" guard (`:118-165`). The Bluebook endpoints are what the pilot exam UI writes sealed exams through; their only exercise is the Playwright job (separate CI job, only 2 endpoints touched). **Fix:** add `tests/test_bluebook_api.py` against `run.load_legacy_demo_app()` (same pattern as `test_pilot_lockdown.py`) covering exam create/list/get, submission recording with tenant scoping, and upload/CSV error paths; unit-test that `lifespan` raises on `ORIGINAL_ENV=pilot` without `SECRET_KEY`.

### T2 — Flag-gated production scoring paths untested through `score()` — **High**
`quantum/scoring.py` is 80%, but the missed lines are precisely the opt-in production features: `_amplitude_score` internals (`:276-318`), the `AMPLITUDE_SCORING_ENABLED` branch in `score()` (`:566-579`), the Bayesian cold-start prior (`:477-495`), the conformal action-nudge (`:971-989`). Building blocks are unit-tested in isolation (`amplitude.py` 99%, `conformal.py` 100%, `null_pool.py` 97%), but no test runs `score()` with these flags ON — the integrated behavior a configured pilot would ship is unverified. **Fix:** parametrized tests calling `score()` under `monkeypatch.setenv` per flag combination, asserting (a) outputs in bounds, (b) flags-OFF output byte-identical to baseline (the project's stated invariant), (c) conformal nudge only ever escalates severity.

### T3 — `store.py` at 73%; Bluebook persistence and most error handlers unexecuted — **High**
Missed block `store.py:1656-1813` is the *entire* Bluebook persistence layer (`put_bluebook_exam`, `put_bluebook_submission`, list/get) — sealed exam evidence is written by code no unit test executes. Remaining misses are paired 2-line `except` handlers (the SQLite failure paths never fire — cf. finding A1). Counterweight: FERPA-critical paths that *are* tested are tested well — deletion purge + receipts, backup scheduler (`backup.py` 87%), tenant-downgrade refusal, `test_store_tenants.py` (17 tests), `test_store_fidelity.py` (28 tests). **Fix:** unit tests for `bluebook_*` store functions (upsert semantics, tenant filtering, malformed `conditions`), plus one injected-`sqlite3.Error` test to confirm except-branches don't swallow corruption silently.

### T4 — `tests/test_api.py` and `tests/conftest.py` test the dormant v1 backend — **Medium**
`tests/conftest.py:32` does `from original.main import app`; every fixture targets the v1 SQLAlchemy stack, and `test_api.py` (26 tests) + `test_auth.py` + `test_canvas.py` hit `/api/v1/*` routes CLAUDE.md declares dormant. The live backend is instead exercised via `run.load_legacy_demo_app()` in the pilot/tenant/lockdown/lti test files. The naming inverts reality: a contributor "adding an API test" will land it in the wrong stack. **Fix:** rename `test_api.py` → `test_v1_api_dormant.py`; factor the live-app `TestClient` pattern into a shared fixture so live-stack API tests are the low-friction default.

### T5 — Quality defects in `tests/test_quantum.py` — **Medium**
Docstring says "Uses Hypothesis" and imports `given`/`st` (line 9) but contains zero `@given` decorators. `test_empty_state` (`:189-199`) is `try/except Exception: pass` with no assertion — it can never fail. `test_authorship_probability_reciprocal_deviation` (`:160-183`) claims to test an inverse relationship but only asserts both values in [0,1]. Vector tests use unseeded `np.random.uniform` with threshold assertions — latent flakiness. ## 4. Accessibility (WCAG 2.1) ✅

**Overall assessment.** The product currently fails WCAG 2.1 at **Level A**, not just AA: the student dashboard's entire sidebar navigation and the Bluebook professor tables are mouse-only, the exam answer textarea has no accessible name, and no error/status message anywhere in the three frontends is announced to screen readers. Basic hygiene is good (every page has `<html lang="en">` and a unique `<title>`, no duplicate static IDs, no zoom blocking), and the newer shared components (`help-hint.js`, `metric.js`, professor's pill/card patterns) show the right ARIA instincts — but the older student.html, all of Bluebook, and the low-alpha "parchment" text palette drag the product well below procurement thresholds (VPAT/Section 508). The highest-stakes flow for accommodations — a screen-reader or keyboard-only student taking a proctored Bluebook exam — is currently **not completable non-visually with confidence** (unnamed answer field, silent proctoring warnings, silent timer).

**Estimate:** roughly 8 of the ~30 applicable A/AA success criteria fail outright (1.1.1, 1.3.1, 1.4.3, 2.1.1, 2.4.6, 3.3.1/3.3.2, 4.1.2, 4.1.3), concentrated in student.html and Bluebook. Failures are highly patterned (five repeated anti-patterns), the shared components already model correct fixes, and there are no architectural blockers. A focused **2–3 weeks** gets to a defensible VPAT; the exam flow (W2/W3/W4) is ~2–3 days on its own.

## 6. Style consistency & SOLID ✅

**Overall assessment.** The live core is stylistically more disciplined than the absence of any lint/format/type config would suggest — quoting, f-strings, and logging discipline are near-uniform, and the quantum/feature math modules are well-documented. The dominant problems are architectural, not cosmetic: `api.py` and `store.py` are god modules, and a deliberately created persistence seam (`repository.py`, ADR-002) is bypassed by 68 direct `store.*` calls in the API layer, so tests fake persistence by mutating module privates. Every production scoring mode is an env-flag-gated block appended inside one 325-line `score()` function — the main open/closed and dependency-inversion liability going forward.

**Consistency scorecard:**

| Dimension | State | Evidence |
|---|---|---|
| Lint/format/type config | **Absent** (tools installed, unconfigured) | default `ruff check original/` → 147 violations; pyproject has no `[tool.*]` |

| String formatting | Consistent — f-strings | 499 f-strings vs 8 `.format()` |

### S1 — `api.py` god module (routing + validation + business logic + persistence + notifications) — **High**
(Same evidence as A2; adds:) the flagship `score_submission` handler (`api.py:1643-1837`, ~195 lines) orchestrates cache stub, adaptive pipeline, impostor-pool build, scoring, three separate persistence writes, report assembly, tension-arc analysis, email notification, and audit logging inline; a 116-line dataclass→pydantic mapper `_to_response` (`:1842`) lives mid-file. **Fix:** APIRouter split by domain + extract `scoring_service.score_and_persist()`.

### S2 — `store.py` second god module: one flat namespace over 12+ table domains — **High**

Every function opens its own connection via `_get_conn()` which replays ~13 DDL statements per open (cross-ref A8). **Fix:** split by aggregate (`store/students.py`, `store/bluebook.py`, …) behind the existing `Repository` protocol; move DDL to one-time `init_db()`.

### S3 — Dependency inversion half-built: Repository seam bypassed 68:26; tests mutate module privates — **High**
`repository.py:5-6` states the contract — "The API layer depends on `Repository`, never on `original.store` directly" — but `api.py` makes **68** direct `store.*` calls vs 26 `_repo()` calls, and reaches into privates (`store._DB_PATH` at `api.py:153,158`). ### S4 — `score()` is a 325-line function growing a flag-gated block per scoring mode, reading config + persistence from inside the math layer — **High**
`quantum/scoring.py:386-710`. Six `os.environ.get()` reads *inside the function body* (`:475,486,515,548,559,564`), each guarding an appended block; the Bayesian branch does `from ..store import get_genre_stats` (`:478`) at call time. The caller independently re-reads four more flags (`api.py:1669-1746`), so flag policy is duplicated across layers. Preserves byte-identical defaults while making each mode testable without `monkeypatch.setenv`.

### S5 — Adding a feature tier requires coordinated edits in ≥3 files / 5 places (Open/Closed) — **Medium**

Special cases already accreting (tier 12 bespoke wrapper, tier 17 inline branch, tiers 9–11 separate paths). Mitigating: ordering is a serialization contract, so full plugin dynamism is undesirable. **Fix:** lightweight declarative registry — each tier module exports `(CODES, BOUNDS, extractor, kind)`; pipeline/constants iterate one ordered `TIERS` tuple. One edit point, ordering still explicit.

### S6 — No lint gate despite tools installed; 86 unused imports accumulating — **Medium**
Default-rules `ruff check original/`: 86 F401 (live examples: `api.py:67`, `api.py:1845` — three names imported-then-unused inside `_to_response`), 12 E712, 5 F841, 1 F811, 6 E741; 18 F821 hits are dormant `db/models/*` forward-refs. **Fix:** minimal `[tool.ruff]` gating `E,F,I` on live modules (`extend-exclude` the dormant tree); autofix F401/I001 in one commit; wire into CI (cross-ref B1). ### S7 — Type-hint coverage varies ~0–100% by module, thinnest exactly at the seams — **Medium**

### S8 — Ten endpoints take raw `body: dict` while ~30 siblings use pydantic — **Medium**

### S9 — Three data-shape idioms meet at hand-written translation layers — **Medium**

## 7. Build pipeline & tooling ✅

**Overall assessment.** The live pilot path (render.yaml → requirements-pilot.txt → `run.py --demo`) is coherent and well-commented, and CI runs the exact documented pytest command plus a real Playwright E2E job — a stronger base than most pilots. But CI has no lint/type-check/coverage/audit gates despite ruff/mypy/black/pytest-cov being *installed* by requirements.txt; there is no check that the committed `bluebook.bundle.js` matches its JSX sources; and the local `.venv` is **Python 3.9.6** while CI/deploy run 3.11 (below pyproject's own `>=3.10` floor). Around the live stack sits a ring of stale deploy targets (fly.toml, Dockerfile, compose, start-prod.sh, alembic — all serving the dormant v1 Postgres backend, untouched since 2026-05-12), plus a security-pin drift where the *pilot* requirements allow the python-jose version range that requirements.txt explicitly bans for CVEs.

### B10 — Pilot requirements permit the CVE'd python-jose range banned in requirements.txt — **High**
`requirements.txt:11-13` documents PYSEC-2024-232/233 (algorithm confusion + JWT decode bypass, fixed in 3.4.0) and pins `>=3.4.0`. But `requirements-pilot.txt:17` — the file the **real pilot deploy** installs (`render.yaml:57`) — pins `python-jose[cryptography]>=3.3,<4.0`. python-jose verifies Canvas LTI id_tokens (`original/lti.py`); an algorithm-confusion CVE in the JWT verifier of the auth path is the worst place for this drift. Pip resolves to ≥3.4 today, but the constraint permits 3.3.0 (stale wheel cache, resolver backtrack). **Fix:** one line — `>=3.4.0,<4.0` in requirements-pilot.txt; then let pip-audit (B4) police this class permanently.

### B2 — No bundle-freshness check: a stale committed bluebook.bundle.js can ship silently — **High**
`demo/bluebook/bluebook.bundle.js` is committed (Render has no Node) and is what `index.prod.html:70` loads in pilot mode. Nothing in CI mentions the bundle; the e2e job runs `npm ci` but never `npm run build`. Today the bundle is fresh — by discipline, not enforcement. The build is deterministic enough for a byte-compare (esbuild pinned via package-lock, fixed concat order in `build.mjs`). **Fix:** in the e2e job after `npm ci`: `npm run build && git diff --exit-code -- demo/bluebook/bluebook.bundle.js`. The single highest-value CI addition for this repo.

### B7 — Local `.venv` is Python 3.9.6; CI/deploy are 3.11; pyproject floor is 3.10 — **High**
`.venv/pyvenv.cfg` says `version = 3.9.6` (Xcode system python), while CI uses 3.11, `render.yaml` sets `PYTHON_VERSION=3.11.0`, all Dockerfiles use `python:3.11-slim`, and pyproject declares `requires-python = ">=3.10"`. Every "passes locally" signal comes from an interpreter two minor versions behind everything that matters. **Fix:** rebuild `.venv` from python3.11; add a preflight assert `sys.version_info >= (3, 10)`; update CLAUDE.md's venv note.

### B16 — `run.py` footguns: destructive seed-by-default; port default contradicts all tooling — **Medium**
(1) `--demo` seeds by default and `seed_demo_store()` calls `store.clear()` first; the hard-refusal only fires for `ORIGINAL_ENV in (pilot, staging, production)`. A developer with `ORIGINAL_DB` pointed at a valuable local SQLite file who runs the documented `python run.py --demo` destroys it. (2) `--port` defaults to 8000 (`run.py:113`) while CLAUDE.md, start.sh, Playwright, and CI all assume 8001. (3) The startup banner advertises stale page names (`original.html`, `original-review.html` — exist only in dead `frontend/`). **Fix:** default port 8001; gate seeding behind explicit `--seed` (flag already exists as a deprecated no-op) or refuse to clear an existing non-seed `ORIGINAL_DB`; fix the banner.

### B15 — Five of eight deploy targets serve the dormant v1 backend, 8 weeks stale — **Medium**
`fly.toml`, `Dockerfile`, `docker-compose.yml`+override, `start-prod.sh`, `docker-entrypoint.sh` — all last modified 2026-05-12; the Docker artifacts run **`original.main:app`** (the dormant v1 Postgres backend) plus Postgres 16 + Redis and `alembic upgrade head`. Anyone who runs `docker compose up` gets the wrong product. `fly.toml` duplicates Render with none of the pilot flags/hardening. Current and healthy: `render.yaml` (2026-07-04) and `deploy/`. **Fix:** move stale artifacts into `deploy/legacy-v1/` with a quarantine banner, or add `# ⚠️ DORMANT v1 stack — the live deploy is render.yaml` headers; README should state render.yaml is the only supported deploy.

### B19 — Alembic is vestigial; the live store has NO migration story — **Medium**
`alembic.ini` targets Postgres; the 7 migrations cover v1 ORM models; only stale v1 artifacts invoke alembic. The live `store.py` manages its own schema with ~18 `CREATE TABLE IF NOT EXISTS` — create-only; adding a column to a table that already exists on the pilot's persistent disk has no path. **Fix:** quarantine alembic/ with the v1 artifacts; more importantly, add a minimal `PRAGMA user_version` migration ladder to store.py *before* the first schema change lands on the pilot DB.

### B1 — No lint/format/type-check anywhere, while the linters ship as runtime deps — **Medium**
CI has only pytest + e2e jobs. `requirements.txt:50-53` pins black/ruff/mypy — installed on every CI run and baked into the production Docker image, never invoked. No ruff/black/mypy config exists; pyproject has no `[tool.*]` sections. **Fix:** fast first CI job `ruff check . && ruff format --check .` (drop black — ruff format subsumes it); move dev tools to requirements-dev.txt; add `[tool.ruff]` to pyproject; introduce mypy incrementally (start with `quantum/` and `store.py`).

### B4 — No dependency-vulnerability or secret scanning, in a FERPA product — **Medium**
requirements.txt is full of hand-maintained CVE annotations — someone does this manually. No pip-audit/safety, no gitleaks, no dependabot.yml. **Fix:** pip-audit CI step (would have caught B10 automatically); Dependabot for pip + npm + github-actions; gitleaks (the repo handles LTI private keys and SECRET_KEYs).

### B6 — Caching half-correct; heaviest artifacts uncached; pytest job over-installs — **Medium**
`cache: pip` keys off requirements hashes, but floating ranges mean resolved versions drift while the key stays constant — and the two CI jobs use different requirements files (different resolution universes). The spaCy model re-downloads in both jobs every run. The pytest job installs full requirements.txt including sentence-transformers → PyTorch (~2 GB) even though the pilot path falls back to TF-IDF. **Fix:** compile locks (`pip-compile`/uv) per target; pin-install the spaCy model wheel by URL (as Dockerfile already does); check whether the suite passes on requirements-demo.txt + dev extras and drop PyTorch from CI.

### B8/B9 — Requirements sprawl: four files, no lock strategy, duplicated pins already drifting — **Medium**
`requirements-pilot.txt` correctly layers on `-r requirements-demo.txt`, but `requirements.txt` duplicates ~11 pins from requirements-demo.txt with copy-pasted CVE comments (matching today; nothing keeps them matched), and `requirements-dev.txt`'s header claims dev-only scope while actual dev tools live in requirements.txt. **Fix:** make `requirements.txt` start with `-r requirements-demo.txt`; relocate pytest/hypothesis/black/ruff/mypy to requirements-dev.txt; generate `*.lock.txt` per target.

### B11 — CI e2e job boots "exactly like the pilot" but installs the wrong requirements — **Low**
The e2e job sets `ORIGINAL_ENV=pilot` but installs requirements-**demo**.txt, not -pilot — so the LTI stack (jose/cryptography) the pilot runs with is never present in E2E, and `/lti/*` routes are untestable there. **Fix:** switch to requirements-pilot.txt (superset, one extra small wheel).

### B5 — Workflow hygiene: no concurrency cancellation, no timeouts, mutable action tags — **Low**
No `concurrency:` block (stacked pushes queue full duplicate runs, each installing PyTorch), no `timeout-minutes` (hung Playwright waits GitHub's 6-hour default), actions pinned to mutable major tags. **Fix:** `concurrency: {group: workflow-ref, cancel-in-progress: true}`; `timeout-minutes: 20`/`15`; pin actions to SHAs.

### B3 — No coverage reporting despite pytest-cov pinned — **Low**
(Cross-ref T9.) **Fix:** `--cov=original --cov-report=xml` + artifact upload; modest `--cov-fail-under`, ratchet later.

### B12/B13 — Bluebook chain: sound tooling resting on manual discipline; unversioned vendored React — **Medium/Low**
`build.mjs` concatenates 10 JSX files in a hard-coded ORDER that "MUST match index.html" — a comment, not a check; no sourcemap (pilot errors point into one minified 94 KB line; esbuild `sourcemap: 'linked'` is free); no size/minification sanity check. Vendored React 18.3.1 is identifiable only by grepping minified source — no VERSION file, no checksums, and nothing pins dev index.html's CDN React to the same version. **Fix:** enable linked sourcemaps; derive ORDER from index.html or assert match; add `vendor/README.md` with versions/URLs/sha256; rely on B2's diff for freshness. (Positive: `playwright.config.mjs` is well-tuned — single worker with documented reason, CI-only retries, trace on-first-retry.)

### B17 — No task runner; six commands retyped constantly, one safety-critical — **Medium**
No Makefile/justfile. Repeated doc-only incantations: test, quantum tests, run server, **bundle rebuild** (whose omission ships stale code), e2e, backup, preflight. **Fix:** ~15-line Makefile (`test`, `test-quantum`, `run`, `bundle`, `e2e`, `backup`, `preflight`, `lint`) hard-coding `.venv/bin/python` — this also mechanically neutralizes the system-python and 3.9-vs-3.11 traps. Also fix `start.sh`: it installs full requirements.txt (PyTorch!) with bare `pip`/`python3` — the broken system python — for a demo needing only requirements-demo.txt.

### B18 — No pre-commit hooks; the Finder-duplicate problem is live right now — **Medium**
`scripts/roster_links 2.py` exists on disk today (plus `tests/test_roster_links 2.py`, §0). Gitignore blocks `* 2.*`–`* 4.*` but does nothing for `git add -f`, patterns ≥5, or ` copy.` names. **Fix — proposed `.pre-commit-config.yaml`:** local hook failing on staged names matching ` [0-9]+\.` / ` copy\.`; `.db`/`.sqlite` blocker (allow `demo/seed.db`); `check-added-large-files --maxkb=500`; ruff + ruff-format; `detect-private-key`; merge-conflict/whitespace hooks (exclude bundle + vendor); pre-push bundle-freshness heuristic. Add `.fuse_hidden*` and `.benchmark_cache/` to .gitignore.

### B20 — Version 0.0.0, zero git tags, no CHANGELOG; deployed SHA recorded nowhere — **Medium**
The pilot is `autoDeploy: false` with manual dashboard deploys — the deployed commit is recorded nowhere in the repo. Render provides `RENDER_GIT_COMMIT` at runtime. **Fix:** surface it in `/health` (fallback "dev"); tag each pilot deploy (`pilot-2026-07-04`); bump pyproject to 0.1.0; one-line-per-deploy CHANGELOG. Skip semver automation — overkill at this scale.

### Proposed minimal-but-complete CI shape
1. **lint** (5 min): ruff check + ruff format --check.
2. **pytest** (20 min, needs lint): install from compiled lock (ideally without PyTorch) + pinned spaCy model wheel → pytest with `--cov=original --cov-report=xml` → coverage artifact → later `--cov-fail-under`.
3. **bundle+e2e** (15 min, parallel to pytest): `npm ci` → **`npm run build` → `git diff --exit-code` on the bundle** → install requirements-**pilot**.txt → Playwright.
4. **security** (10 min, non-blocking initially): pip-audit + gitleaks.
Workflow level: concurrency cancel-in-progress, SHA-pinned actions, `permissions: contents: read`, dependabot.yml (pip/npm/actions).

## 10. Postgres convergence plan (migration to the dormant backend's data layer) ✅

**Scope decision (proposed ADR-006).** "Migrate to the dormant backend" is implemented as: **the live API keeps its routes and behavior; its persistence moves to Postgres through the Repository seam; the v1 stack's infrastructure (SQLAlchemy models, alembic, pydantic Settings) is promoted to live; the v1 API surface is deleted.** This is exactly the convergence ADR-002 designed `repository.py` for. A wholesale switch to `original/main.py` would regress the pilot: the v1 API has no Bluebook, no live LTI (`/lti/*`), no calibration lab, no null model, no voice/formation surface, and a different auth model.

**Current state (measured):** `Repository` protocol covers 9 methods (formation ×3, tenants ×4, audit ×2) of the store's **67 public functions across 16 tables** (`student_profiles`, `users`, `tenants`, `student_names`, `submission_manifests`, `fidelity_scores`, `ai_likelihood_scores`, `corrections`, `calibration_runs`, `tuned_thresholds_v`, `bluebook_courses/exams/submissions`, `formation_pathways`, `baseline_requests`, `audit_log`). v1 has 7 model files (`baseline`, `canvas`, `course`, `institution`, `student`, `submission`, `user`) covering perhaps a third of that surface. `api.py` bypasses the seam 68:26; `quantum/scoring.py` calls the store directly (A5); `PostgresRepository` raises on every method; `get_repository()` always returns SQLite.

### Phase P0 — Decision & infrastructure (2–3 days)
- Write ADR-006 (this scope decision, with the retirement list). Provision Render Postgres (staging first; `databases:` block in render.yaml), `DATABASE_URL` secret.
- Promote and adapt v1's `core/config.py` pydantic `Settings` as the live config object (also closes A7/F3's scattered-env problem); merge `ORIGINAL_ENV`/`ENVIRONMENT`.
- Prerequisite from WS-7 step 1: `ScoringConfig` + genre-stats-as-parameter, so no scoring code touches persistence directly.

### Phase P1 — Widen the seam (1–2 weeks, pure refactor, SQLite still the backend)
- Extend the `Repository` protocol from 9 → full coverage of the 67 store functions, grouped by aggregate (students, baselines, scores, manifests, corrections, calibration, thresholds, tenants, users, bluebook, audit, roster, formation, baseline-requests, genre-stats).
- Mechanically route api.py's 68 direct `store.*` calls through `_repo()`; remove the `store._DB_PATH` private reaches (`api.py:153,158`) behind a `Repository.db_info()` method.
- Convert `test_store_tenants.py` / `test_store_fidelity.py` / new bluebook tests into **repository contract tests**: one parametrizable suite run against any `Repository` implementation. *Accept:* full suite green with zero behavior change; api.py imports `store` only via `SqliteRepository`.

### Phase P2 — Schema & models (1–2 weeks)
- Model the 16 tables in SQLAlchemy 2.x. Reuse v1 models where they genuinely fit (`user`, `student`, `institution`≈`tenants`) and extend; write new models for the other ~12. Delete `canvas.py`/`course.py` models unless the Canvas import path needs them.
- **Design decisions to make deliberately:**
  - *Tenancy:* replace the `"{tenant_id}:{local_id}"` string-prefix key convention (`store.py:1962-1979`) with a real `tenant_id` column + FK + composite unique constraint. Provide a compatibility shim at the repository boundary so the API's existing ID scheme keeps working during migration. This turns tenant isolation from a convention into a constraint — the single biggest correctness upgrade of the whole migration.
  - *Density matrices / vectors:* keep the existing serialization functions (numpy → bytes) targeting `BYTEA`; feature vectors and JSON blobs → `JSONB`. The 28 `test_store_fidelity.py` round-trip tests are the safety net.
  - *Timestamps:* ISO strings → `timestamptz` at the column level; repository returns the same string shapes the API expects (no API change).
  - *Transactions:* store today is autocommit-per-call; give `PostgresRepository` a session-per-request pattern (FastAPI dependency), which also fixes A8's connection churn on the SQLite side if backported.
- Reset alembic: archive the 7 stale v1 migrations, generate a fresh baseline migration from the new models (B19 resolved — alembic becomes the live migration story).

### Phase P3 — PostgresRepository + parity (2–3 weeks)
- Implement per aggregate, in dependency order: tenants/users → students/baselines → scores/manifests → bluebook → calibration/corrections/thresholds → formation/audit/requests.
- Run the P1 contract suite against Postgres in CI (service container: `postgres:16`); every aggregate lands only when its contract tests pass on both backends.
- Property test the round-trip: `fidelity(ρ_in, ρ_out) ≈ 1.0` for random density matrices through the Postgres path.

### Phase P4 — Data migration & shadow validation (1 week + 1–2 week soak)
- `scripts/migrate_sqlite_to_pg.py`: read via SqliteRepository, write via PostgresRepository; per-table row counts + content checksums; explicit report artifact. FERPA note: run on the Render host or over an encrypted tunnel; no student data on laptops.
- Optional but recommended (the repo already has a shadow-mode culture): `REPO_SHADOW=postgres` — writes mirrored to both backends, reads from SQLite, divergences logged. Soak for 1–2 weeks of pilot traffic.
- Backup story: switch OPS_RUNBOOK from `backup.py` file copies to Render managed backups + nightly `pg_dump`; rehearse a restore before cutover.

### Phase P5 — Cutover (one maintenance window)
- Freeze writes (maintenance flag) → final sync run → flip `get_repository()` to Postgres for the pilot env → run PILOT_SMOKE_TEST → unfreeze. Keep the SQLite file read-only on disk for ≥4 weeks as instant rollback (flip the env var back).

### Phase P6 — Decommission & unlock (1 week)
- Demote the in-memory `_STORE` dict: reads go through the repository; keep at most a bounded per-request cache (A4, A8). **This unlocks `--workers N` and Render scaling** — move the login throttle to the DB or accept per-worker limits explicitly.
- Delete the v1 API surface: `original/api/`, `original/canvas/`, `original/main.py`, `original/middleware/`, `original/auth/`, `original/schemas_v1/`, plus their 62 tests (`test_api.py`, `test_auth.py`, `test_canvas.py`, v1 fixtures in conftest) (F1, T4, T6). Deleting `original/api/` dissolves the module-shadowing collision — `run.py`'s importlib hack goes away without renaming anything (A9).
- Delete `frontend/`, `web/`, `legacy_mvp/`; update or delete Dockerfile/docker-compose/fly.toml to target the converged stack (B15, F6).
- Keep (now live): `original/db/` models, alembic, `Settings`.

**Risks & mitigations:** SQLite→PG dialect drift (SQLAlchemy abstracts it; contract tests catch the rest) · migration data loss (checksums + shadow soak + rollback file) · Render Postgres cost (~$7–20/mo pilot tier — confirm before P0) · long-tail store functions with subtle semantics (`tuned_thresholds_v` versioning, audit pagination — port with their tests first) · timeline pressure mid-pilot (every phase before P5 is shippable-inert; P5 is the only user-visible moment and it's one maintenance window).
