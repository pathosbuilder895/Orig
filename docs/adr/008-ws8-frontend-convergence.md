## Context

### What WS-8 planned

One Vite + React + TypeScript workspace at `app/`. Phase R0 scaffolds it; R1
folds `demo/bluebook/` into it ("convert the 11 global-scope `.jsx` files to
real ESM"; "kill the ORDER comment forever"); R2 builds a shared accessible
component library; R3 migrates the eleven static `demo/*.html` pages into it
page by page; R4 cuts each page over at its existing path. Accessibility is
the acceptance criterion throughout — "axe zero serious/critical" per PR — and
that standing gate is what makes the VPAT (WS-3/D15) writable from evidence
rather than hope.

### What actually happened

Measured on `main`, 2026-08-02:

| WS-8 phase | Planned | Actual |
|---|---|---|
| R0 — workspace | Vite/TS/vitest/axe scaffold at `app/` | **Done.** `app/` exists, CI job runs lint + typecheck + vitest + build. `App.tsx` renders "No page has been migrated here yet." |
| R1 — Bluebook folds in | Bluebook rebuilt inside the `app/` Vite workspace | **Not done, and independently superseded.** Bluebook converted itself to real ESM, deleted the `ORDER` array, and bundles React as a real dependency — via its own 30-line `build.mjs` esbuild pipeline (`demo/bluebook/build.mjs`), not Vite. R1's *substantive* goals are met; its *structural* goal (one workspace) is not. |
| R2 — component library | Accessible primitives, each with an axe test | **Done, in `app/`.** 10 primitives, 2,414 LOC of TS/CSS, 75 vitest+axe tests, all green. |
| R3 — page migration | 11 static pages → React | **Not started.** All ten remaining `demo/*.html` pages — 11,500 lines — still served as-is (`landing.html` was retired separately, by WS-7 step 5). |
| R4 — cutover | `dist/` served at each page's path | **Not started.** `app/dist` is gitignored; nothing mounts it; `run.py:80` mounts exactly one static directory. |

So the tree contains two React frontends. One of them serves every user
Original has. The other serves none.

### The five facts that make this a decision rather than a scheduling problem

**1. The deploy model admits one committed bundle at a time.** Render builds
no JavaScript. What production serves is the *committed* artifact —
`demo/bluebook/bluebook.bundle.js`, ~300 KB, regenerated by hand and guarded by
test.yml's byte-identical freshness check. WS-8 acknowledges this and proposes
generalizing the pattern, but "generalize" here means a second committed
bundle, a second freshness gate, a second thing that ships stale silently, and
a second static mount in `run.py`. The constraint is not fatal to any option —
it is simply much cheaper to satisfy once than twice.

**2. `app/` and Bluebook are not the same kind of code.** Bluebook is `.jsx`
with no type layer, styled entirely by inline style objects drawn from a
JavaScript palette (`BB` in `components.jsx`), and contains **zero `.css`
files**. R2's primitives are `.tsx`, each importing a sibling `.css` that
`@import`s `tokens.css`. Dropping `LabeledInput` into `Exam.jsx` means either
teaching esbuild a CSS pipeline and reconciling two token systems, or
rewriting the primitive in Bluebook's inline-style idiom — which is a port,
not an adoption.

**3. `tokens.css` was derived from the legacy statics, not from Bluebook.**
Its own header says so: values "ported from the converged `:root` custom
properties in `demo/student.html` and `demo/professor.html`". The palettes
genuinely differ (`--color-parchment: #f7f2e7` vs `BB.parchment: #F4EFE6`;
`--color-gold: #b08d3c` vs `BB.gold: #C9A961`). The R2 library is already
tuned for the pages in **Option B's** scope and mistuned for Bluebook.

**4. The a11y gate moved, and its promotion path no longer exists.** WS-8
assumed axe pressure would arrive with the React rebuild. It arrived first,
somewhere else: `demo/bluebook/e2e/a11y.spec.mjs` (WS-9 Stage 2) runs 13 cases
on every PR — twelve axe scans across the Bluebook screens and `parked.html`,
plus a keyboard-walk — all tagged `@a11y` and non-blocking. Its docstring says
a page's case is "promoted to blocking only once WS-8 lands that page's React
rebuild" — but WS-8 never plans to *rebuild*
Bluebook, only to relocate its build. Read literally, no Bluebook screen can
ever qualify for promotion. The gate that WS-8 exists to make writable is
today parked behind a condition WS-8 will not produce. Meanwhile R2's 75 axe
assertions run against components no user reaches.

**5. `app/` is not free while it waits.** 23 devDependencies against
Bluebook's 3; 15 of the 17 commits ever made to `app/package.json` are
dependabot bumps, including majors (`eslint` 9→10, `typescript` 5→7, `jsdom`
25→29). Every one is a PR to review and a CI run to watch, spent on a
workspace serving no traffic. That is the ongoing price of the current
undecided state, and it is paid whether or not R3 ever begins.

## Options

Each table rates the option's own cost, not its desirability.

### Option A — Retrofit: adopt R2 primitives inside Bluebook, retire `app/`

Move the primitives into `demo/bluebook/`, converting them to Bluebook's idiom
(or teaching `build.mjs` to handle CSS and TS), adopt them screen by screen
behind the existing `@a11y` scans, then delete `app/`. The ten remaining
statics stay static, addressed later or never.

| | |
|---|---|
| **Complexity** | **High.** Two conversions, not one: TS→JSX (or JSX→TS) *and* CSS→inline-style (or esbuild→CSS pipeline). Token reconciliation is a design decision per value, not a find-and-replace — Bluebook's palette is the one users see, so R2's WS-4-corrected contrast values must be re-derived against `BB`, not copied. |
| **Cost** | ~2–3 weeks. Each of 10 primitives ported and re-tested; each of 9 screens migrated onto them; bundle re-committed each time. R2's 75 tests do not survive the port — they are vitest/jsdom, and Bluebook has no unit-test harness at all, only Playwright. |
| **Risk** | **Highest of the three.** Every change lands directly in the exam-taking path. Bluebook is what a student sits in front of during a proctored exam; a regression there is not a cosmetic bug. Mitigated by 71 Playwright tests, but those assert flows, not pixels — a broken parchment palette or a lost focus ring passes them. |
| **Buys** | The a11y primitives arrive where the users and the live axe scans already are. One frontend, one build, one bundle, one dependency set. `@a11y` promotion becomes achievable. |
| **Costs** | The ten remaining statics — including the 5,050-line `professor.html`, the worst-measured page — are left untouched with no plan. Discards R2's test suite and its typing. |

### Option B — Amend: Bluebook's pipeline is permanent; scope `app/` to the legacy statics

Declare `demo/bluebook/` + esbuild the permanent home of the exam app and stop
trying to fold it in. Keep `app/` and R2, and re-aim WS-8's R3 at what it was
always really about: the ten static pages, 11,500 lines of HTML. Two frontends, on
purpose, with a stated boundary.

| | |
|---|---|
| **Complexity** | **Moderate at the seam, high in total.** No conversion work — R2's tokens already match the statics it would serve. But it requires the thing fact 1 warns about: a second committed `dist/`, a second freshness gate, a second `run.py` static mount, and a documented rule for which frontend a new page belongs to. |
| **Cost** | R3 as originally scoped: ~6–10 weeks of page migration, `professor.html` alone 3–4 of them. Plus ongoing dual maintenance — two dependency sets, two toolchains, two upgrade streams, indefinitely. |
| **Risk** | **Moderate and slow-acting.** Two component vocabularies drift; a fix lands in one and not the other. The migration is long enough that the "one release" `?legacy=1` windows WS-8 specifies will be tempting to leave open, which is the drift WS-8's own risk section names. |
| **Buys** | Every line of R2 is used as built. Honest about a fork that already exists rather than pretending it is temporary. The statics — where the measured a11y findings are worst — finally get addressed. |
| **Costs** | Commits to the highest total effort and the only permanent dual-maintenance burden. Pays fact 5's dependabot tax forever, now justified. |

### Option C — Sunset `app/` and R2; port primitives into Bluebook on demand

Delete `app/` (recoverable from git). Bluebook is the frontend. When a
Bluebook screen needs an accessible dialog or a labelled input, write it in
Bluebook, consulting R2's implementation in history for the hard parts —
focus trap, `useId` wiring, `aria-describedby` composition. The statics keep
receiving WS-4-style targeted fixes.

| | |
|---|---|
| **Complexity** | **Lowest.** One deletion. No conversion, no second pipeline, no token reconciliation. |
| **Cost** | Near zero now; small and recurring later, paid only when a screen actually needs a primitive. |
| **Risk** | **Low on delivery, real on principle.** Nothing users touch changes. The risks are (a) discarding good work — 2,414 lines and 75 tests that genuinely encode the WS-4 findings; (b) losing the *forcing function*: R2 in the tree is a standing argument that primitives should exist, and deleting it makes "just add another `<div onClick>`" easier; (c) the statics stay unmigrated with no successor plan at all. |
| **Buys** | Removes the largest live plan-vs-reality gap in the repo in one commit. Ends the dependabot tax. Leaves exactly one frontend, which the deploy model prefers. |
| **Costs** | Throws away the only artifact that captured the audit's a11y findings as code. Least ambitious on accessibility, which is the outcome WS-8 exists to produce. |

## Recommendation

**Option B, with one amendment that borrows from A.**

The reasoning turns on fact 3 and fact 4 together. The R2 library is not a
generic component library that happens to have no consumers yet — its tokens
were derived from `student.html` and `professor.html`, so it is *already the
right library for the statics* and the *wrong* library for Bluebook. Option A
asks it to serve a codebase it was not built for, paying a conversion cost
twice over to reach screens whose a11y is already being watched every PR by
`a11y.spec.mjs`. Option C throws away the only code in the repo that encodes
the WS-4 findings as enforced behaviour, at the moment the VPAT still needs
that evidence. Option B is the only one that spends R2 on what it was measured
against — and `professor.html`, 5,050 lines and the worst-scoring page in the
audit, is the single largest accessibility liability Original has. It is not
addressed by A or C at all.

The amendment: **fix the `@a11y` promotion path first, before any page
migration, and independently of which option is chosen.** `a11y.spec.mjs`
gates promotion-to-blocking on a Bluebook React rebuild that no option
delivers. Rewrite that condition to what actually matters — a screen's `@a11y`
case becomes blocking once it passes clean, whatever it is built from — and
Bluebook's screens become promotable immediately, on their existing
markup. That is a few hours of work and a WS-9 doc edit, and it converts a
parked gate into a live one without waiting on a ten-week migration. It is
also the honest version of what WS-8 promised: accessibility as an acceptance
criterion, applied to the pages that have users.

Adopting B means accepting a permanent fork and saying so: `demo/bluebook/` +
esbuild owns the exam application; `app/` + Vite owns the staff/administrative
pages migrated out of `demo/*.html`; a new page joins whichever side its users
are on. The second committed bundle and its freshness gate are the price, and
they should be built once at the start of R3 rather than discovered during the
first cutover.

**If the owner is not prepared to fund 6–10 weeks of R3, recommend Option C
over Option B.** B's cost-benefit rests entirely on the statics actually being
migrated. An `app/` workspace kept alive for a migration that never starts is
strictly worse than deleting it: the same dependabot tax, the same two
toolchains, and none of the accessibility payoff. Between "B, eventually" and
"C, now", C is the more honest answer. Option A is not recommended in any
scenario — it carries the highest risk, in the exam path, for a benefit the
live `@a11y` scans plus the amendment above deliver more cheaply.

## Consequences if Option B is adopted

- WS-8's R1 is closed as **superseded, not done** — Bluebook met R1's real
  goals (ESM, no ORDER array, bundled React, dev/prod parity) by another
  route. `build.mjs` becomes a supported build, not an interim one.
- `docs/implementation/WS-8-react-migration.md` needs its R1 section and its
  "one workspace" framing amended by its owner. This ADR does not edit it.
- A second committed-`dist` + freshness gate + static mount lands before R3
  page 1, not during it.
- `a11y.spec.mjs`'s promotion condition is rewritten and Bluebook screens are
  promoted to blocking as they pass — a WS-9 change, doable now.
- The dependabot cost on `app/` is accepted deliberately, against a scheduled
  migration.

## What would change this recommendation

- **R3 is not funded.** → Option C. See above; this is the most likely trigger.
- **Bluebook's `@a11y` scans start failing in ways its own idiom cannot fix**
  (rather than the contrast-blend artefacts already diagnosed and settled by
  the spec's `settle()` helper) → Option A gains real weight, because then the
  primitives are needed *in the exam path* and the conversion cost buys
  something urgent.
- **Render gains a Node build step, or the API moves behind a static site**
  (audit §11 option (b)) → fact 1 dissolves, the second-bundle cost mostly
  disappears, and B gets materially cheaper.
- **The VPAT ships, or is dropped.** The evidence requirement is a large part
  of why R2 is worth keeping; without it, C's case strengthens considerably.
